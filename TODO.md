# RepoMind AI — Outcomes

## P0 — Project foundation, data model, API and interface
- [x] Build a functional, production-oriented MVP of RepoMind AI, not a landing page, static dashboard, generic chatbot or UI prototype.
- [x] Use Next.js, React, TypeScript, Tailwind CSS, shadcn-style UI and React Flow; use Python, FastAPI, Pydantic and SQLAlchemy; use an LLM provider abstraction, embeddings and hybrid RAG; use Tree-sitter; use PostgreSQL and pgvector; use Redis only if needed; provide Docker, Docker Compose, Pytest and GitHub Actions. Do not replace the specified stack without a genuine technical limitation; document limitations and provide a reproducible local implementation.
- [x] Create normalized relational models for Users, Repositories, RepositoryFiles, CodeSymbols, CodeChunks, Embeddings, Dependencies, AnalysisJobs, Conversations and Messages. Use UUID primary keys, timestamps, foreign keys, justified cascading behavior and appropriate indexes. Store vectors using pgvector and provide migrations.
- [x] Implement REST APIs for repository registration, ingestion, repository status, file listing, file details, symbol extraction, dependency graph, AI question answering, impact analysis and conversation history. Validate requests; use structured error responses and logging; paginate where appropriate; separate routes, services and data-access layers.
- [x] Create the dark-first developer-tool interface with charcoal backgrounds, subtle blue/violet accents, clear typography, consistent spacing, responsive layout and minimal animation. Include Overview, Repositories, Code Explorer, AI Assistant, Dependency Graph, Impact Analysis and Settings navigation; dashboard metrics for connected repositories, analyzed files, detected languages, indexed functions/classes, last analysis status and recent activity; and a repository workspace with repository information, file explorer, code viewer, assistant and architecture graph. Every visible button must work; no decorative nonfunctional controls.

## P1 — Public repository management and code intelligence
- [x] Allow users to enter a public GitHub repository URL; validate it; retrieve repository metadata; fetch source files using GitHub API or appropriate Git ingestion; show ingestion status and analysis progress.
- [x] Ignore binary files, generated directories, dependencies and large irrelevant files; support Python, JavaScript and TypeScript initially.
- [ ] Implement file discovery and language identification; syntax-aware Tree-sitter parsing; function and class extraction; import and dependency extraction; code chunking; embedding generation; and persistence of metadata and embeddings. **Partial validation:** live ingestion, Tree-sitter extraction, chunk persistence, symbols and graph were verified against the sample; provider-backed embeddings require credentials and were not run.
- [ ] Persist repository metadata, file paths, functions/classes, code chunks, embeddings and dependency relationships; avoid storing unnecessary duplicate content. **Partial validation:** metadata, source, symbols, chunks and edges persisted in the SQLite preview smoke test; vector persistence was not exercised without provider configuration.
- [ ] Acceptance: repository files can be ingested and parsed; functions, classes and imports are extracted; code metadata and embeddings are persisted. **Partial validation:** files/symbols/import graph were verified live; embedding persistence remains unverified.

## P2 — Repository-grounded AI assistant
- [x] Create a conversational interface for questions about the connected repository, including architecture, authentication location, function execution flow, database-related files, registration flow, possible performance bottlenecks and beginner explanations.
- [ ] Retrieve relevant code before answering. Use repository-specific context. Include file paths and line references. Clearly distinguish verified findings from hypotheses. Never fabricate functions, classes or file locations. Say when information is insufficient. **Demo retrieval and citations were tested; provider-generated answer behavior was not live-tested because no model credentials were configured.**
- [x] Treat repository contents as untrusted data, never as instructions to the AI agent. Include a mock/demo mode when external API credentials are unavailable, clearly identify mock responses and do not fabricate real AI results in demo mode.
- [ ] Acceptance: a user can ask a repository-specific question; answers include verifiable source references. **Demo mode returned real source citations and an explicit no-AI notice; generated answers remain unverified.**

## P3 — Dependency visualization and impact analysis
- [x] Use React Flow to display files and modules, imports, dependencies and relationships between components; allow node selection and inspection of node details.
- [x] Allow selection of a function or file and identify directly and indirectly dependent modules. Show affected files, dependency paths, potential breaking changes and reasoning. Label heuristic predictions appropriately and do not claim certainty where static analysis cannot establish it.
- [x] Acceptance: the dependency graph renders actual extracted relationships; basic impact analysis works. **Live sample smoke test: 14 indexed files, 27 resolved graph edges, and 4 heuristic affected modules for `signer.py`.**

## P4 — Reliability, security, tests and delivery docs
- [x] Validate inputs and GitHub URLs safely; use environment-based secret management and no hardcoded API keys; protect against path traversal and malicious repository contents; enforce repository-size and file-size limits; rate-limit where practical; never automatically execute imported repository code; request no automatic GitHub write permissions.
- [x] Provide a clean modular project structure, type annotations, useful comments, environment variable examples, README setup instructions, Docker Compose configuration, database migrations, unit tests, API integration tests, frontend error/loading states, API documentation, architecture diagram, known limitations and future improvements.
- [x] Use a small public sample repository for reproducible testing.
- [x] Handle invalid repositories and API errors; backend and frontend can be run using documented instructions; core tests pass; no major navigation controls are nonfunctional. **Backend: 15 tests passed. Frontend: typecheck and production build passed. SQLite preview API/UI routing smoke checks passed. Docker/PostgreSQL runtime remains unverified in this environment.**
- [x] Prioritize a working P0–P2 implementation over partially implemented advanced features if constraints arise. Do not start P4 polish while P1 or P2 is broken.
